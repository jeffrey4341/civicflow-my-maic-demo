# CivicFlow 政府互操作与公共服务统一路线图设计

> 日期：2026-08-10
>
> 状态：书面规格已由产品负责人于 2026-08-10 批准；实施规划进行中
>
> 变更类型：设计与路线图规格；不代表未来功能已经实现
> 当前产品边界：公开 MAIC T5 合成数据演示；不是政府生产系统

## 1. 执行决策

CivicFlow 的长期目标不是用一套巨型软件替换所有政府部门系统，而是统一公共服务的体验、案件语义、跨部门交接、政策证据、人工治理和审计协议，同时让各部门继续持有自己的权威系统与法定决定权。

一句话定位：

> **CivicFlow is an AI-assisted, human-governed interoperability and casework layer for Malaysia's federated public services — one service experience, many systems of record.**

中文表达：

> **CivicFlow 是马来西亚联邦式公共服务的 AI 辅助、人工治理互操作与案件协作层：统一服务体验，但保留多个部门权威系统。**

AI 能显著降低多语言理解、服务分类、旧字段映射、SOP 检索、摘要草拟和异常对账成本，因此让“统一服务体验与协作协议”变得可行。AI 不能自动解决法定权限、采购、预算、数据所有权、跨部门责任或最终行政决定，因此不能把“统一”解释为全国数据库集中化或所有系统一次性替换。

## 2. 已确认的产品选择

### 2.1 首个采用范围

- 从 **一个 PBT** 开始。
- 先建立所有旅程共用的可信案件与治理核心。
- 按顺序验证三条不同风险类型的跨部门旅程：
  1. 商业执照；
  2. 水灾／排水；
  3. 教育／福利。
- 只有前一阶段通过结果、安全、可靠性和责任门，才能扩大部门或机构范围。

### 2.2 “统一”的准确含义

统一以下内容：

- 市民一次描述问题、获得一个追踪编号和一致的状态回执；
- 共同服务目录与标准案件信封；
- 跨部门交接、补件、SLA、责任人和事件语义；
- 政策出处、人工决定、审批和审计证据；
- 连接器的安全、可靠性、认证与退出协议；
- 四语言服务结果的一致性评估。

不统一以下内容：

- 不替换所有部门应用、数据库、GIS、工单、财政或许可系统；
- 不建立保存所有敏感政府数据的中央数据湖；
- 不自建公民国家身份系统；
- 不把法定授权或行政责任转移给 CivicFlow 或 AI；
- 不让 AI 自动决定资格、批准高风险事项、执法、付款、派工或关闭案件；
- 不在没有法定依据、机构批准和独立验证时宣称政府生产就绪或全国采用。

## 3. 路线选择

| 路线 | 优点 | 主要失败风险 | 决策 |
|---|---|---|---|
| 全国替换／集中化套件 | 理论统一度最高，中央入口直观 | 巨型迁移、采购与治理冲突、敏感数据集中、权威来源模糊、前线拒用和锁定 | 拒绝作为主路线；统一入口可以存在，但数据留在来源机构；替换模块只用于没有既有系统的绿地范围 |
| 受治理集成与协调层 | 最快验证真实价值，保留部门所有权 | 连接器碎片、双写、状态漂移 | **0–12 个月采用**，以严格契约、幂等、对账和责任边界控制风险 |
| 联邦协议与公共平台 | 长期降低接入成本和厂商锁定 | 没有独立采用者时会成为纸面标准 | **12–36 个月演进方向**，必须有多机构治理和至少两个独立实现 |

选择是：**集成／协调层 → 经验证的联邦协议**，不是一次性替换全部政府软件。

## 4. 产品核心与差异化

模型本身不是护城河。CivicFlow 的核心是“受治理的公共服务案件协作”。

### 4.1 市民侧核心

- 一个移动优先入口，支持 Malay、English、Chinese、Tamil；
- 一次提交、一次补件、一个跨部门追踪编号；
- 显示案件由谁处理、当前状态、需要什么资料、下一步是什么；
- 回复说明政策依据和人工责任，不伪装成 AI 已经作出政府决定；
- 保留柜台、代理和非智能手机替代渠道，不以数字身份排除弱势群体。

### 4.2 公务人员侧核心

- 一个以案件为中心的工作台，不要求人员理解每个旧系统；
- AI 提供分类、路由、字段映射、缺件检测、政策检索、摘要和回复草稿；
- 人员确认或覆盖 AI 建议，覆盖原因成为评测与改进数据；
- 高风险、资格和正式行动进入明确人工审批门；
- 每次交接都有接收方、SLA、政策版本和完整时间线。

### 4.3 政府治理核心

- 每项可执行建议都有已批准政策引用，否则进入人工复核；
- 每项决定性动作都可归因到获授权人员；
- 每次状态变化都生成追加式审计事件；
- 每个部门系统继续是其业务领域的 system of record；
- 所有外部写入都经过机构批准的连接器和原系统权限模型；
- 连接器失败必须可见、可重试、可对账和可回滚。

### 4.4 最重要的产品特色

1. **政策有据**：不是聊天答案，而是带版本、出处与置信度的公共服务建议。
2. **人类负责**：AI 草拟和推荐；人员批准、发送、执行、判定和关闭。
3. **跨部门但不夺权**：统一案件体验，保留部门数据和权威系统。
4. **多语言结果公平**：不仅翻译界面，还比较四语言在分类、路由、引用、缺件和审批结果上的差异。
5. **可审计、可解释、可退出**：机构能重建完整决策链，也能更换连接器或供应商。

## 5. 当前仓库基线

当前仓库已证明 Phase 0 的演示论点：

- 四语言移动端案件输入；
- 确定性语言识别、分类、政策检索、路由、缺件检测、审批规则与回复草拟；
- 引用或人工复核；
- 高风险主管审批；
- 人员复核、回复释放、开始处理和关闭的分离动作；
- 合成政策和合成案件；
- 进程范围的追加事件时间线；
- 无模型 API key 也能运行。

当前尚未实现、不得描述为已经完成：

- 持久数据库、数据库迁移与恢复；
- 机构／租户隔离；
- 生产身份、会话、RBAC/ABAC、职责分离或紧急访问；
- 正式 SOP 与数据治理流程；
- 真实部门系统、MyGDX、MyDigital ID 或通知连接器；
- 生产级不可变账本、监控、灾备、事件响应、安全认证；
- 任何政府采用、采购、数据共享或生产托管批准。

本设计不得改写 Phase 0 的公开演示事实，也不得把未来路线加入“当前功能”清单。

## 6. 目标架构

```text
Citizen channels                    Officer / supervisor workspace
mobile · counter · assisted         queues · cases · approvals · audit
            \                                  /
             +-------- CivicFlow experience ---+
                              |
              Shared governed casework core
      service catalog · case envelope · workflow/state machine
      policy evidence · human approval · audit · SLA · notifications
                              |
                  Bounded AI assistance
      language · classification · mapping · retrieval · summary · draft
                              |
                   Governed connector boundary
      scoped authority · idempotency · outbox/retry · dead-letter
      versioned events · reconciliation · rollback · certification
                              |
     +------------------------+-------------------------+
     |                        |                         |
 Licensing system      GIS / work orders       Welfare / finance
     |                        |                         |
     +---------- Agency-owned systems of record -------+

Cross-cutting trust plane:
identity federation · tenant isolation · purpose-bound access · data
classification · keys · monitoring · incident response · BCP/DR
```

### 6.1 责任边界

| 层 | CivicFlow 负责 | CivicFlow 不负责 |
|---|---|---|
| 体验 | 一次提交、统一追踪、补件和状态解释 | 取代所有部门门户 |
| 案件协作 | 标准状态、交接、SLA、审批与审计 | 覆盖部门法定流程 |
| AI | 理解、检索、映射、异常发现、建议和草稿 | 最终行政决定或不可逆行动 |
| 连接器 | 受权访问、转换、投递、重试、对账、证据 | 绕过原系统权限或成为影子权威库 |
| 数据 | 最小工作副本、引用和必要缓存 | 集中复制全部部门数据 |
| 身份 | 适配 MyDigital ID、机构批准的 OIDC 身份服务和公务人员身份联合 | 自建国家身份或保存生物识别资料 |

### 6.2 标准契约

| 契约 | 最小内容 | 验收要求 |
|---|---|---|
| `ServiceDefinition` | `service_id`、司法辖区、主管机构、材料、政策依据、SLA、允许动作 | 每条旅程先有已批准服务定义 |
| `CaseEnvelope` | CivicFlow ID、外部案件 ID、correlation ID、所有者、参与部门、状态、数据分类 | 每个字段、决定和状态维度有且仅有一个明确权威来源；CivicFlow 只权威记录协调状态与自身审计 |
| `CaseEvent` | 版本、事件 ID、幂等键、行为人、前后状态、时间、来源、理由 | 重放不产生重复决定或写入 |
| `PolicyCitation` | 政策 ID、版本、章节、片段、置信度、批准状态 | 建议 100% 有引用或转人工 |
| `DecisionRecord` | 决定类型、人员身份、授权范围、证据、理由、时间 | 所有决定性动作 100% 人工可归因 |
| `ConnectorManifest` | 系统所有者、能力、凭证范围、字段映射、SLA、重试、退出 | 通过沙盒、故障、越权和对账测试才启用 |
| `DataUseContract` | 目的、法源／协议、字段、接收方、保留、地域、审批、撤销 | 默认拒绝；按目的和最小数据授权 |
| `IdentityContext` | 机构、人员／公民主体、角色、属性、委托、会话、认证强度 | 服务端验证，客户端字符串不构成权限 |

## 7. AI 的可行范围

| AI 可辅助 | 必须由确定性规则／人员控制 |
|---|---|
| 语言检测与翻译辅助 | 身份认证、权限和职责分离 |
| 服务分类与紧急信号提示 | 法定资格、许可、处罚与付款决定 |
| 旧字段到标准字段的建议映射 | 数据共享法源和批准 |
| SOP／FAQ 检索与政策引用 | 工作流状态机和高风险审批门 |
| 缺件发现、摘要、回复草稿 | 派工、执法、关闭和正式发送 |
| 同步异常聚类与对账建议 | system-of-record 最终状态 |
| 四语言结果差异检测 | 审计写入、保留与事故响应 |

任何模型错误、低置信、无引用、风险不明或契约不匹配都走 default-deny：转人工、阻止外部写入并记录原因。

## 8. 三条服务旅程

以下部门链是等待首个 PBT 验证的目标流程假设，不是当前仓库事实，也不代表真实 PBT 已批准。Phase 1 必须由业务、政策、数据和系统负责人共同批准对应 `ServiceDefinition`，才可把链路作为正式试点流程；实际责任链不同则更新服务定义，不强迫机构迁就演示流程。

### 8.1 商业执照：第一条受控试点

```text
Citizen → Licensing → Public Health → Engineering → human-issued outcome
```

- AI：识别执照类型、抽取地点／业务类型／营业时间、检索材料清单、草拟补件通知。
- 人员：确认分类与完整性；各部门接受或拒绝交接；获授权人员作出正式许可结果。
- 系统：执照系统为正式结果权威来源；CivicFlow 保存交接证据和状态引用。
- 证明目标：一般行政服务是否能减少重复录入和跨部门等待。

### 8.2 水灾／排水：第二条公共安全旅程

```text
Citizen → Engineering → Public Health → Community & Welfare → authorised work order
```

- AI：识别水位／积水／卫生风险、提取地点、检索响应 SOP、建议优先级和摘要。
- 人员：确认风险、批准升级、决定是否发出工单或跨部门支援。
- 系统：GIS／资产／工单系统保持派工与完成状态的权威来源。
- 证明目标：紧急案件可加速，但不让 AI 绕过公共安全和派工责任。

### 8.3 教育／福利：第三条资格敏感旅程

```text
Citizen → Community & Welfare → Finance → Education → human eligibility outcome
```

- AI：预筛服务类别、生成文件清单、检索政策、摘要已有材料。
- 人员：核实资料、评估资格、确认预算／付款与正式结果。
- 系统：福利、财政和教育系统分别保持其法定记录；CivicFlow 不生成 AI 资格决定。
- 证明目标：同一核心能处理最高治理敏感度，而不是只做低风险投诉。

## 9. 36 个月分阶段路线图

所有数字都是进入下一阶段前的目标假设，不是当前成果。试点前先测量基线；若实证表明目标不合理，必须记录原因并经治理负责人批准调整，不能事后降低安全门。未经授权决定、危险门绕过、跨租户访问或无法解释的状态变化属于安全触发器，发生一次即暂停相关试点；价值或采用指标未达标则不得进入下一阶段，但不等同于安全事故。

### Phase 0 — 当前：MAIC 合成演示

**目标：**证明产品论点，不假装生产。

**完成定义：**三个代表性服务领域的演示路径、引用、人工审批、人员决定、追加事件和无 key 确定性运行均可重复验证；数据保持 100% 合成。当前路径证明治理逻辑，不代表真实跨部门系统已经连接。

### Phase 1 — 0–3 个月：一个 PBT 的可信核心

**交付：**

- 持久数据库、迁移、备份、恢复与保留；
- `agency_id`／`pbt_id`、数据和政策隔离；
- 服务端会话、身份、RBAC/ABAC、职责分离；
- 服务目录、案件／事件／政策／决定契约 v0.1；
- 政策版本与负责人批准；
- 受保护的 admin/reset；
- 监控、限流、安全日志和事件责任人；
- 合成连接器沙盒与故障注入。

**阶段门：**

- 至少 200 个四语言评估案件；
- 至少 1,000 次状态转换与权限测试；
- AI 建议 100% 有引用或人工复核；
- 决定性动作 100% 归因到获授权人员；
- 状态变化 100% 记录行为者，行为者可以是人员或具名系统组件；
- 高风险绕过、跨租户访问、未授权外部写入均为 0；
- 沙盒 connector delivery event 成功率 ≥99%，所有差异都能检测与对账；
- 恢复演练和关键安全门通过。

**停止／转向：**

- 第 30 天仍没有业务、系统和数据负责人；
- 第 60 天仍没有获批准沙盒或接口路径；
- 无法建立现有流程基线；
- 存在未解决的严重身份、隔离、审计或恢复缺口；
- 方案要求 AI 执行决定性动作。

### Phase 2 — 3–6 个月：商业执照受控试点

**交付：**

- 在同一 PBT 内验证 Licensing → Public Health → Engineering 的交接；没有获批 API 的环节先采用明确责任人的人工交接，不伪造系统集成；
- 连接一个获批准的权威案件／执照系统和一个通知通道；
- 最小权限和用途绑定凭证；
- 幂等、事件版本、outbox/retry、dead-letter、对账与回滚；
- 人工覆盖原因、同步失败、政策版本和语言质量仪表板；
- 运行、恢复、回滚与事故响应手册。

**阶段门：**

- 受控运行至少 8 周并累计至少 300 个获批案件，以较晚者为准；
- 中位分流时间相对基线下降 ≥30%；
- 首次回复资料完整率提升 ≥15 个百分点；
- 高风险人工门覆盖率 100%，错误放行为 0；
- connector delivery event 成功率和服务时段可用性 ≥99.5%；
- 所有同步差异在一个工作日内完成对账；
- 高置信分类／路由的实质性人工修改率 <25%。

**停止／转向：**

- 8 周后分流改善不足 15%；
- 路由实质修改率连续 4 周 >30%；
- >2% 案件因同步错误需要线下修复；
- 发生未经授权的决定性动作、危险门绕过或无法解释的状态变化时立即暂停。

### Phase 3 — 6–12 个月：同一 PBT、三条旅程

**交付：**

- 在同一核心依次加入水灾／排水和教育／福利；
- 至少三个部门使用共同服务、案件、事件、政策和审批模型；
- 建立跨部门交接接受／拒绝、责任人、SLA 和统一回执；
- 只共享完成交接所需字段；
- 发布契约 v1 候选版，但不宣称国家标准。

**阶段门：**

- 三条旅程端到端可追踪率 100%；
- 高风险与资格决定人工处理率 100%；
- 严重审计缺口、跨部门越权和自动决定均为 0；
- 成对同义四语言评测的实质结果不一致率 <5%；
- 核心代码的旅程专属产品分支为 0；
- canonical field/event reuse ratio ≥70%，即跨三条旅程使用公共定义的字段与事件占全部字段与事件定义的比例。

**停止／转向：**

- 新旅程必须复制独立产品或绕开共同契约；
- 第二或第三条旅程不能重复首条旅程的价值；
- connector mapping component reuse ratio <40%，即第二、第三条旅程复用首条旅程的连接器配置、转换和对账组件比例过低；
- 资格或公共安全责任无法明确归属。

### Phase 4 — 12–24 个月：多机构联邦协议

**范围：**在法律、机构和数据负责人批准后，扩到 2–5 个机构，或“一州 + 2–3 个 PBT”。Sabah、Sarawak 和半岛需按各自法律与实施轨处理。

**进入条件：**第 12 个月开始多机构扩展前，必须已有获参与机构认可的治理章程、有协调权的公共数字服务主体，以及明确的数据责任、事故责任和契约变更权。未满足则保持 Phase 3 单 PBT 产品，不启动多机构扩展。

**交付：**

- 服务／案件／事件／政策／同意／审计契约 v1；
- 连接器注册、兼容性测试、认证与参考适配器；
- 身份联合、委托授权、租户隔离和机构退出；
- 数据共享协议、字段级最小化、保留和密钥责任；
- 独立隐私、安全、灾备和审计评估；
- 允许其他厂商实现协议，而不要求采用 CivicFlow UI 或运行时。

**阶段门：**

- 至少两个独立团队／厂商实现协议；
- 新连接器中位上线时间 ≤4 周；
- 至少 70% 字段和事件使用公共定义；
- 跨机构转交与决定审计覆盖 100%；
- 兼容性测试通过率 ≥90%；
- 没有跨租户政策、身份或数据泄漏。

**停止／转向：**

- 多机构治理章程、协调主体或责任模型失效且无法恢复；
- 第 24 个月仍无 CivicFlow 以外的独立实现；
- >30% 正常场景依赖机构／厂商私有扩展；
- 数据、事故或标准变更责任长期无法确定。

### Phase 5 — 24–36 个月：受治理的跨层级服务网络

**方向：**在获授权范围连接地方、州与联邦服务；适配 MyGOV、MyDigital ID、机构批准的身份联合协议和 MyGDX，数据尽量留在来源机构。

**交付：**

- 共享服务目录和跨层级案件状态；
- 协议治理委员会、版本迁移和兼容性窗口；
- 认证连接器生态、供应商中立采购与退出方案；
- 分层部署；按数据分类由获授权的马来西亚公共机构或批准运营方控制密钥；配套监控和 BCP/DR；
- 市民可查看参与服务的统一状态，同时机构保留权威记录。

**雄心指标，不是承诺：**

- 10 个机构、20 条完整服务旅程；
- 至少两个独立协议实现持续运行；
- 新机构中位接入时间 ≤4 周；
- 新机构实施成本相对首个试点下降 ≥50%；
- 参与服务中 ≥90% 案件能显示统一状态；
- ≥95% 状态事件在 5 分钟内同步；
- 人工归因、政策出处和审计覆盖保持 100%；
- 自动资格决定、高风险批准、派工和关闭保持 0。

**停止／收缩：**

- 没有跨层级采用或独立实现者时，保持专业 PBT 集成产品；
- 接入成本随机构数量增加；
- 扩展要求集中复制全部部门敏感数据；
- 协调层成为不可隔离的安全或可用性单点故障；
- 机构因失去 system-of-record 权而拒绝采用。

## 10. 指标体系

### 10.1 北极星

> 市民只提交一次，并通过一个追踪编号获得政策有据、人工负责、跨部门可追踪的结果。

### 10.2 结果指标

- 端到端完成率；
- 中位分流与跨部门交接时间；
- 首次回复资料完整率；
- 重复录入次数与人工接触次数；
- SLA 内完成比例；
- 市民能够理解“当前状态／负责人／下一步”的比例。

### 10.3 治理与安全指标

- 引用或人工复核覆盖率；
- 决定性动作人工归因率；
- 高风险门覆盖率；
- 未授权决定、门绕过、跨租户访问和无法解释状态变化数量；
- 审计事件完整率与政策版本可追溯率；
- 数据共享目的、最小字段、保留和审批覆盖率。

### 10.4 AI 与公平指标

- 分类／路由的人类接受率和实质修改率；
- 无引用、低置信和转人工比例；
- 成对同义四语言评测的实质结果不一致率：分类、路由、引用、缺件或审批门出现实质差异的语言对数量，除以全部被评测语言对数量；
- 误报／漏报的风险信号；
- 模型版本、提示、政策语料和评测集可追溯率。

### 10.5 互操作指标

- connector delivery event 成功率：在统计窗口内成功投递并获目标系统确认的到期事件数，除以全部到期投递事件数；只有事先批准的计划维护窗口可以排除，排除量必须单独报告；
- 服务时段可用性：计划服务分钟减去非计划不可用分钟，再除以计划服务分钟；事先批准的计划维护另报；
- canonical field/event reuse ratio 衡量公共语义定义覆盖；connector mapping component reuse ratio 衡量连接器配置、转换和对账组件复用，两者不得混用；
- 新服务、连接器和机构的接入时间与成本；
- 私有扩展比例；
- system-of-record 状态与 CivicFlow 状态差异率。

## 11. 法律、国家架构与部署约束

截至 2026-08-10，本设计采用以下官方方向作为路线约束，而不是声称当前仓库已经合规或获批：

- [Malaysia Digital 2030](https://www.digital.gov.my/en-GB/siaran/Kementerian-Digital-Terajui-Transformasi-AI-Negara) 强调 Whole-of-Government、端到端在线服务、MyGOV 和下一代数字公共基础设施；CivicFlow 应成为可接入 GovTech 的案件互操作层，而非竞争性国家超级应用。
- [RMK13](https://rmk13.ekonomi.gov.my/wp-content/uploads/2025/09/120925-Main-Document-e-Book.pdf) 强调公共部门 Enterprise Architecture、Government-as-a-Platform、integration/interoperability 和减少孤岛；Phase 1 必须先固化服务目录与目标架构。
- [MyGovEA 服务架构](https://mygovea.jdn.gov.my/page-arkitektur-perkhidmatan/) 与 [DDSA](https://sddsa.jdn.gov.my/) 提供模块化、多租户、SSO、互操作和数据标准方向；标准字段应先映射 DDSA，而非另造不可兼容词汇。
- [MyGDX](https://www.digital.gov.my/en-GB/siaran/Revolusi-Digital-Sektor-Awam%3APPDSA-Dan-MyGDX-Pemacu-Transformasi-Rakyat) 是现有跨机构交换设施；CivicFlow 规划 MyGDX-ready 适配器和案件编排，不另建全国数据交换中心。
- [MyDigital ID](https://www.digital-id.my/en/about) 是未来公民认证适配方向；具体协议由获批准的接入规范决定。公务人员身份联合必须与公民身份分开。
- [Data Sharing Act 2025 (Act 864)](https://www.jdn.gov.my/akta-perkongsian-data-2025-akta-864/) 的直接范围是联邦政府及相关法定机构。州和 PBT 数据共享不能只靠技术接通，必须逐案法律审查并确认适用的授权依据；协议、合同或 MoU 可以是治理文件，但其存在本身不证明法源充分。
- 若具体部署被认定为 NCII 或落入 [Cyber Security Act 2024 (Act 854)](https://www.nacsa.gov.my/act854.php) 的适用范围，才承担相应法定义务；是否适用须由机构法律、安全和数据负责人逐案确认。[National Cloud Computing Policy](https://www.digital.gov.my/api/file/file/FINAL%20-%20MALAYSIA%E2%80%99S%20NATIONAL%20CLOUD%20COMPUTING%20POLICY%20%28MNCCP%29.pdf) 作为数据分类、云部署、安全控制、密钥、监控和灾备的政策设计依据。公开演示托管不能代表政府生产托管。
- [PDPA Act 709](https://www.pdp.gov.my/ppdpv1/wp-content/uploads/2024/07/UNDANG-UNDANG-MALAYSIA_AKTA_PERLINDUNGAN_DATA_PERIBADI_2010_709_MALAY_AND-ENG_V2022.pdf) §3(1) 不适用于 Federal Government 和 State Governments，不能作为政府数据保护的完整法律依据；PBT 适用性和公共部门数据治理要求须逐案法律审查。
- [AIGE](https://ai.gov.my/ethical-guide-ai) 当前可作为人工监督、透明、可靠、安全、隐私与问责设计基线。任何 AI 治理法案仍需 policy-watch，不能在正式生效前写成现行强制法律。

每个真实连接器在启用前必须有机器可读的目的、法源／协议、数据分类、字段、接收方、保留、审批、凭证范围和撤销规则。默认拒绝，最小数据，逐用途授权。

## 12. 运营与治理角色

每条已接入服务至少要有以下明确责任人：

- 服务负责人：拥有业务结果和 SLA；
- 政策负责人：批准政策来源、版本和解释；
- 数据负责人：批准用途、字段、保留与接收方；
- 系统负责人：拥有 system-of-record 和连接器变更；
- 安全／隐私负责人：批准风险、事件和部署边界；
- 运营负责人：负责失败队列、对账、恢复和市民升级；
- 模型负责人：负责评测、版本、偏差和人工覆盖分析。

缺少任一关键责任人时，该服务不得计为“已接入”。Phase 4 起需建立跨机构协议治理与变更委员会；CivicFlow 团队不能单方面改变公共契约。

## 13. 关键风险与缓解

| 风险 | 早期信号 | 缓解／停止动作 |
|---|---|---|
| 连接器动物园 | 每条旅程都有独立字段和专属分支 | 公共契约、配置映射、复用门；低于门槛停止横向扩展 |
| 双写与状态漂移 | 大量线下修复、责任不清 | 明确权威来源、outbox、幂等、对账、回滚；超过 2% 暂停 |
| AI 被当成决策者 | UI 或审计找不到人员身份 | 技术禁止自动决定，人员归因 100%，出现一次立即暂停 |
| 无引用或过期政策 | 建议无法重建依据 | 政策版本、负责人批准、引用或转人工、过期阻断 |
| 数据集中化 | 连接器要求复制全部数据 | 最小工作副本、来源读取、purpose-bound access；无法避免则不接入 |
| 多语言不公平 | 同义请求得到不同实质结果 | 四语言对照评测、人工复核、差异 <5% 门 |
| 纸面标准无人采用 | 只有 CivicFlow 实现协议 | Phase 4 要求两个独立实现，否则保持产品而非公共协议 |
| 规模先于价值 | 机构数上升但时间／成本没有改善 | 每阶段 outcome gate；首个试点无价值则退回单领域产品 |
| 供应商锁定 | 无法导出、迁移或替换连接器 | 开放契约、审计导出、版本迁移、退出测试 |

## 15. 验收结论

这条路线允许 CivicFlow 最终影响大量政府服务，但不以“所有部门使用同一个软件”为成功定义。真正的成功是：

- 市民不再重复理解政府组织结构或重复提交相同资料；
- 部门不用放弃现有权威系统也能协作；
- AI 降低语义与行政准备成本，但不夺走责任；
- 每项跨部门结果都有政策、人、时间和系统证据；
- 新机构的接入时间和成本随协议成熟而下降。

如果这些结果不能在一个 PBT 的三条旅程中被证明，就不应扩大到全国；如果能够被证明，联邦协议才是可持续扩展路径。
